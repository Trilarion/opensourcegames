# Open Source Games List - Project Architecture

## Overview

**OSGL** (Open Source Games List) is a curated database of open source games, game tools, frameworks and libraries
(2,000+ entries) with special emphasis on technical information like availability of sources, licenses, programming
languages or build information. The website is published from `docs/` via GitHub Pages.

The project consists of:

- **Content**: 2,000+ human readable markdown entry files (`entries/*.md`), one per game/tool/framework/library,
  following the format of `template.md` (field meanings in `definitions.md`, contribution rules in `CONTRIBUTING.md`)
- **Metadata**: Developer and inspiration information (`developers.md`, `inspirations.md`)
- **Website**: Static HTML site (`docs/`) generated from the above
- **Maintenance Tools**: Python package `osgl` (`code/`) for validating, enriching, synchronizing and publishing data

## Repository Layout

```
AGENTS.md, README.md, CONTRIBUTING.md, LICENSE
template.md           # template of an entry (also the marker used to find the repository root)
definitions.md        # meaning and allowed values of the entry fields
developers.md         # developer details (contacts, homepages, ...)
inspirations.md       # inspiration details (media links, ...)
improvements.md       # hand-written list of games that could easily be improved
statistics.md         # generated statistics
entries/*.md          # the entries (source of truth)
entries/tocs/         # generated tables of contents (by type, category, platform)
entries/screenshots/  # screenshot images and their generated README.md
docs/                 # generated static website (do not edit by hand)
code/                 # Python package, tests, scripts and data files (see code/README.md)
local-config.ini      # local settings, not tracked in Git
private.properties    # API tokens (GitHub/GitLab), not tracked in Git
```

### Generated content

Several files are (partly) generated by the tools and must not be edited by hand; regenerate them instead:

- `README.md` (section between the "autogenerated content" comments) and `entries/tocs/*.md`:
  `osgl.maintenance.entries` → "Update Readme and TOCs"
- `statistics.md`: `osgl.maintenance.entries` → "Update statistics"
- `entries/screenshots/README.md`: `osgl.maintenance.screenshots`
- `docs/` (HTML pages, copied static assets and screenshots, `docs/data/entries.json`): `osgl.website.generate`
- `code/archives.json`: `osgl.maintenance.entries` → "Update repository list"
- Website icon font (`code/src/osgl/website/static/css/fonts/osgl.ttf`/`.woff`): `code/scripts/build_icon_font.py`
  from the SVG sources in `code/src/osgl/website/icons` (provenance in its README)

## Architecture

### Data Sources
1. **Entry files** - Markdown files with game/tool information (languages, licenses, platforms, repositories, etc.)
2. **Developer/Inspiration lists** - Curated markdown with metadata, partly extracted from the entry files
3. **External sources** - GitHub, GitLab, Codeberg, SourceForge, LibreGameWiki, osgameclones, awesome lists and
   Wikipedia, used by import/synchronization tools to find new entries or update existing ones
4. **Git repositories** - Ability to locally archive the game repositories (git, hg, svn) for preservation

### Processing Pipeline
```
External sources → Import/sync tools (human reviewed) → Entry files + listings
Entry files + listings → Parse (Lark) → Validate → Generate README/TOCs, statistics, website
Entry files → Repository list → Local archive → Git statistics
```
The website generation works only on the local files, it does not call external APIs.

### Python Codebase (`code/`)
Package `osgl` in `code/src/osgl` (not installed during development, used from the source tree with `code/src` on the
Python path), tests in `code/tests` (pytest), one-off scripts in `code/scripts`, data files (backlog, rejected list,
archive lists, import progress) directly in `code/`.
- **Core** (`osgl/*.py`): Parsing (`parse.py`), entry/developer/inspiration I/O (`osg.py`), paths and constants
  (`constants.py`), generic helpers (`utils.py`), statistics, rejected entries, archive helpers
- **Grammars** (`osgl/grammars`): Lark grammars for the entries and the listing files
- **Maintenance** (`osgl/maintenance`): Interactive Qt tools for entries, developers, inspirations and screenshots
- **Archiving** (`osgl/archiving`): Clone/update the local repository archive, submodule detection, git statistics
- **Sync** (`osgl/sync`): Import and synchronization scripts for the external sources
- **External** (`osgl/external`): Wrappers around the GitHub, GitLab and Wikipedia APIs
- **Website** (`osgl/website`): Static website generator with Jinja templates and static assets
- **UI** (`osgl/ui.py`): Qt/PySide6 helpers for the maintenance interfaces

## Python execution

Python may be run (e.g. `python`, `pytest`) for verification or maintenance, but only with the currently active
project environment.

- The package `osgl` is not installed in the active environment during development; it is used directly from within
  the repository. Put `code/src` on the Python path (`PYTHONPATH=src` inside `code/`) and run tools as modules,
  e.g. `python -m osgl.website.generate`. pytest does this automatically (`pytest.ini`), and so do the VS Code
  terminals (`.vscode/settings.json`). The `osgl-*` commands are therefore usually not available.
- Tests: run `pytest` inside `code/`; `pytest -m fast` for quick tests, `pytest -m slow` for the tests that process
  the whole database.
- The maintenance tools (`osgl.maintenance.*`) open an interactive Qt UI and are meant to be run by the maintainer;
  prefer testable plain functions and pytest for verification.
- Never create virtual environments or other Python environments.
- Never install, upgrade or uninstall packages (no `pip install`, `uv`, `conda`, ...), this includes installing the
  `osgl` package itself. The maintainer sets up the environment.
- If a dependency is missing, stop and report what is missing instead of installing it.

## Git

- Commits typically go straight to the default branch (`master`), no feature branches are needed in this repository except when explicitly asked for.
- Commit only when asked to.
- Never pull or push; the maintainer does all pulling and pushing.

## Python documentation style

Before editing Python code, read and follow the **Docstring Style** section in
`code/README.md`. In particular, function and class docstrings must use a
multi-line layout: place the opening triple quotes on their own line and begin
the documentation text on the following line. Do not use one-line docstrings.

## Key Principles

- **Single source of truth**: Entry files are authoritative; other data syncs from them. In particular, the entries
  (`Developer` and `Inspiration` fields) define which developers worked on which projects and which inspirations a
  project has. `developers.md` and `inspirations.md` only keep additional details (contacts, homepages, media links,
  ...) and must adapt to changes in the entries (renamed, added or removed entries). Changes affecting these
  mappings should update the entries and both listings together, to avoid inconsistencies (planned: tooling that
  does this in one step, with tests to follow).
- **Generated files are outputs**: Change the entries or the generator, then regenerate; never edit generated
  content by hand.
- **Consistency over perfection**: Regular maintenance checks find and report issues
- **Pragmatic validation**: Lark grammars enforce entry format; runtime checks catch logical errors
- **Interactive maintenance**: Tools use a Qt UI for human-in-the-loop operations
- **Statistical analysis**: Statistics are calculated from the entries to detect entries that could be improved
